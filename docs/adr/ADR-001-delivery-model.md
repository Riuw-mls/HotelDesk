
# ADR-001: Выбор модели доставки (Delivery Model)

Статус: Принято

Дата: 2026-09-15

## Контекст

Проект — веб-система Hotel Booking System, реализуемая двумя студентами. Требования могут уточняться в процессе разработки, требуется регулярная демонстрация промежуточных результатов в течение семестра. Небольшой состав команды и необходимость частой обратной связи требуют модели доставки, поддерживающей итеративную поставку и возможность переприоритизации задач.

## Драйверы решения

* изменение требований
* небольшой размер команды
* регулярная обратная связь
* инкрементальная доставка
* ограниченное время на разработку
* возможность переприоритизации задач

## Рассмотренные варианты

### Вариант 1 — Predictive / Waterfall

Преимущества:

* Чёткое планирование и фиксированный объём/сроки.
* Удобно для определения больших вех и контрактных обязательств.

Недостатки:

* Низкая гибкость при изменениях требований.
* Риск несоответствия результата эволюционирующим ожиданиям заказчика.

Причина отклонения:

Waterfall не подходит при ожидаемых изменениях требований и необходимости частых демонстраций в рамках семестра.

### Вариант 2 — Adaptive / Scrum

Преимущества:

* Поощряет инкрементальную поставку и частую обратную связь.
* Позволяет переприоритизировать работу между спринтами.
* Подходит для небольших кросс-функциональных команд.

Недостатки:

* Требует дисциплины в планировании и поддержке бэклога.
* Возникает дополнительная нагрузка на планирование и коммуникацию.

Причина выбора:

Adaptive/Scrum обеспечивает необходимую гибкость, быстрые циклы обратной связи и возможность фокусироваться на приоритетных функциях в пределах семестра.

### Вариант 3 — Гибридный (Hybrid)

Преимущества:

* Комбинирует предсказуемость для ключевых вех и гибкость для деталей.

Недостатки:

* Более сложное управление процессом и ролями.
* Риск неясности границ между предсказуемой и гибкой частью процесса.

Причина отклонения:

Гибридный подход добавляет лишнюю сложность и процессные издержки для двухчленной студенческой команды и может снизить скорость разработки.

## Решение

Выбрана модель Adaptive / Scrum. Для данного проекта Scrum позволяет проводить короткие итерации, регулярно демонстрировать результаты преподавателю, быстро адаптироваться к изменяющимся требованиям и фокусироваться на MVP в рамках семестра.

## Последствия

### Положительные последствия

* проще адаптироваться к изменяющимся требованиям
* регулярная обратная связь
* инкрементальная разработка
* возможность переприоритизировать функции

### Отрицательные последствия / компромиссы

* более частое планирование
* необходимость поддерживать бэклог
* окончательный объём работ может измениться
* требуется дополнительная коммуникация между двумя участниками команды
* сложнее точно прогнозировать итоговый объём работ

## Отклонённые альтернативы

* Predictive (Waterfall) — отклонён из‑за низкой гибкости и рисков при изменяющихся требованиях и ограниченном времени.
* Hybrid — отклонён из‑за добавления сложности и процессных издержек для небольшой команды.
